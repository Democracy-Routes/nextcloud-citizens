# Running an assembly

This section is for the organizer, the person who plans an assembly, runs it from a laptop and
owns the report afterward. The pages follow the order of a real event.

| Stage | Page |
|---|---|
| Learn the vocabulary | [Concepts](concepts.md) |
| Prepare: settings, consent, phones, rehearsal | [Before the day](before-the-day.md) |
| Run: recorders, Live tab, captions, replacements | [On the day](on-the-day.md) |
| Finish: review, report, publish, retention | [After the assembly](after.md) |
| Brief the person at each table | [Facilitator guide](facilitator.md) |
| Turn findings into a Polis conversation | [Polis consultation](polis.md) |
| Bring a session in, or rescue a failed table | [Recovery and import](recovery-import.md) |

Audio is the primary record, and no software guarantees capture through a dead battery, a
killed browser, a lost microphone or erased browser storage. The procedures in this section
are arranged so that any of those is an annoyance, not a lost table.
[Recording pipeline and reliability](../architecture/recording-pipeline.md) describes what
the software can and cannot survive.

Administration tasks (keys, providers, backups) are in [Administration](../admin/index.md).
Every action in the interface has an organizer route; they are in the
[API reference](../reference/api/index.md).
